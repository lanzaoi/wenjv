# ADR 0001: 向量存储引擎技术选型: LanceDB vs pgvector (Vector Storage Engine Selection)

## 状态 (Status)

**Accepted** (已采纳)

## 背景与架构语境 (Context)

wenjv（问据）知识库定位为轻量级、低维护成本、高度隐私自托管的知识管理与检索增强生成 (RAG) 系统。系统采用混合检索与异步分块入库架构，需要对底层的向量数据库引擎进行确定性的技术选型。

评估核心聚焦于两个备选方案：
1. **LanceDB**: 嵌入式列式存储向量引擎，基于 Apache Arrow 与 Lance 文件格式，支持零额外服务依赖与本地文件读写。
2. **Postgres + pgvector**: 传统的客户端与服务端关系型数据库扩展，具备成熟的 ACID 事务特性、多并发写入能力及运维生态。

## 决策 (Decision)

**当前默认使用 LanceDB 作为主向量存储引擎；该方案能够满足个人与小团队知识库的应用规模需求；当面临团队级多节点密集写入场景时，通过适配层评估接入独立数据库服务**。

具体决策依据如下：

1. **零外部服务依赖与极简部署**
   wenjv 知识库的核心设计目标之一是开箱即用。LanceDB 属于嵌入式引擎，随 Python 进程直接启动并读写本地磁盘目录（`~/.config/wenjv/lance_db/`，自动兼容回退 `~/.config/inquisitive/lance_db/`），无需用户配置独立的数据库容器、管理连接池或维护常驻后台服务进程。
2. **满足目标规模性能要求**
   在个人应用场景下（通常为万级至十万级切块规模），LanceDB 基于 Arrow 的内存映射查询能够保持毫秒级响应延迟。配合 SQLite FTS5 倒排索引，能够满足日常高频问答与检索的性能要求。
3. **架构适配层隔离与可插拔性**
   系统通过 `backend/vector_store/adapter.py` 对向量引擎进行了统一抽象封装。底层业务代码不直接依赖 LanceDB 的专有 API，保留了通过配置开关路由至其他向量后端的架构弹性。

> [!IMPORTANT]
> **真实性声明**: 当前系统在发布基线中**完全基于 LanceDB 运行**，代码库未将 pgvector 列为生产依赖项。规范严格记录当前代码事实，不提前声明未经验证的技术组件。

## 结果与后置影响 (Consequences)

### 正向收益
- **降低系统资源开销**：宿主机内存占用低，适用于个人服务器、NAS 及工作站本地自托管部署。
- **备份与恢复便捷**：向量索引与 SQLite 数据库保存在同一宿主机目录下（`~/.config/wenjv/`，自动回退兼容 `~/.config/inquisitive/`），迁移或备份时直接打包数据目录即可完成。

### 约束与演进路径
- **并发写限制**：LanceDB 依赖底层单机文件锁机制。面对团队级多用户高频持续写入场景时，存在写锁等待排队。
- **演进路线**：当知识库未来走向大规模团队多写并发场景时，系统可基于现有适配器接口，扩展接入独立数据库服务（如 Postgres + pgvector）以满足高频写吞吐需求。
