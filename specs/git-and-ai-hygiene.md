# Git 与工程卫生规范 (Git & Engineering Hygiene)

规格决定工程边界，版本控制与自动化测试保障交付质量。
本文档为工程执行细则，涉及协作流程时以本规范为准。

---

## 1. 核心原则

1. **范围锁定**：单次任务仅修改预定范围内的模块与文件，未经确认不得擅自扩大变更路径。
2. **变更可审计**：每个提交单元必须明确阐述变更内容、修改原因以及可独立复现的验证方法。
3. **人工确认门禁**：提交信息、分支推送及范围变更必须经人工审核确认。
4. **验证实事求是**：严格区分冒烟测试、单元测试与集成测试，以实际命令退出码与输出日志为准。
5. **文档代码同步**：系统行为与接口契约调整时，必须同步更新 `specs/` 对应文档。

---

## 2. 任务上下文与边界约束

委派实现任务时，上下文必须明确声明：

```text
- 任务目标：<任务名称>
- 允许修改路径：<文件路径列表>
- 执行约束：禁止无关格式化、禁止全量暂存 (git add .)、禁止强推、严禁提交真实凭证
- 验收准则：<执行命令及期望输出>
- 参考规范：specs/README.md 及相关技术规格
```

若执行过程中发现需扩大变更范围，应当暂停修改，待变更范围评估确认后另建新任务推进。

## 3. 版本控制纪律 (Git Hygiene)

### 3.1 高危受限命令

| 命令与操作 | 限制原因与风险分析 |
|------------|--------------------|
| `git push --force` / `--force-with-lease` | 破坏团队协作历史与远程引用分支 |
| `git reset --hard` | 容易导致本地未提交的工作成果丢失 |
| `git clean -fd` | 容易误删未跟踪的工程文件或配置文件 |
| 对已推送提交执行 `amend` 或变基操作 | 篡改公共历史导致协作分支产生分叉冲突 |
| 修改全局系统级 `git config` | 污染宿主机开发环境配置 |
| 删除 `.git` 目录 | 导致版本控制元数据不可逆丢失 |

### 3.2 推荐标准操作

- 查询状态与对比变更：`git status`、`git diff`、`git log`
- 精确暂存与提交：`git add <精确文件路径>` 配合 `git commit`
- 创建与切换特性分支：根据规范要求检出独立分支

### 3.3 暂存与提交检查清单

```text
规范做法：
1. git status 确认改动文件列表
2. git diff 检查具体代码变更
3. git add path/to/file1 path/to/file2 精确添加
4. git diff --cached 确认待提交内容
```

提交前检查项目：

- [ ] 确认未混入 `.env`、密钥、虚拟环境目录、本地数据库及大型二进制模型
- [ ] 确认未混入无关文件的全局自动格式化
- [ ] 确认未混入临时调试脚本或测试日志
- [ ] 确认仅包含当前任务允许变更的文件

### 3.4 提交信息规范 (Commit Message Conventions)

采用 Conventional Commits 格式：

```text
<type>: <简明摘要说明>

[可选正文]
- 修改原因
- 验证命令与结果
```

| 提交类别 (type) | 适用场景 |
|-----------------|----------|
| `feat` | 新增业务功能或架构特性 |
| `fix` | 修复缺陷与异常流转问题 |
| `docs` | 补充或修改技术文档与规范 |
| `test` | 新增或调整自动化测试用例 |
| `refactor` | 重构代码结构，不改变外部功能契约 |
| `chore` | 构建流程、依赖或配置文件调整 |
| `perf` | 性能优化 |

原则：
- 单个提交保持原子性，聚焦单一意图。
- 严禁模糊摘要（例如 `update`, `fix bug`, `wip` 等）。

### 3.5 分支管理命名规范

```text
feat/<特性主题>
fix/<缺陷主题>
docs/<文档主题>
```

按任务逻辑规划提交，保持提交树清晰可读。

## 4. 交付验证与合并门禁

在完成代码修改与合并前，依照以下步骤执行验证：

```text
1. 检查代码 Diff: 确认变更未超出范围，未泄漏敏感信息
2. 运行自动化测试: 确认测试命令执行成功且无报错
3. 抽检核心链路: 针对改动的 API、上传或鉴权链路进行功能核对
4. 同步更新规范: 调整变更所影响的技术规格与文档
5. 精确原子提交: 执行路径暂存并编写规范提交信息
```

### 4.1 验证结论表述规范

| 合格表述 | 不合格夸大表述 |
|----------|----------------|
| `pytest tests/ -q` 输出 4 passed | 仅执行基础冒烟却宣称“全量测试通过” |
| 运行针对性测试脚本返回期望状态码 | 未连接真实模型服务却宣称“端到端验证通过” |
| 在接口文档中验证接口调用正常 | 仅验证通信畅通却宣称“完成深度安全审计” |

### 4.2 测试异常处置原则

- 严禁通过删除断言、滥用跳过装饰器或编写空异常捕获来换取测试变绿。
- 当测试与新业务规范冲突时，更新测试用例并明确记录契约演进原因。

---

## 5. 凭据隔离与安全准则

- 真实生产密钥、Token 及密码严禁提交至代码仓库。
- 日志输出与提交记录中禁止包含完整的 Authorization 请求头或凭据内容。
- 严格遵循 AGPL-3.0 许可协议，不添加与开源许可冲突的限制性声明。
- 示例配置统一使用通用占位符（如 `your_api_key_here`）。

---

## 6. 环境一致性与路径规范

- 新增模块导入需同步更新至 `requirements.txt`。
- 避免盲目升级重大主版本依赖。
- 禁止将本机开发机绝对物理路径硬编码至源码中，统一通过配置或相对路径解析。
- 脚本中需兼顾 Windows 与 POSIX 环境的路径格式差异。

---

## 7. 代码规范与冗余清理

提交代码应保持整洁：

- 清理未使用的 import 语句与已失效的注释代码
- 杜绝裸异常捕获（如 `except:` 无类型捕获且吞掉异常）
- 消除重复注册的路由与重复实现的工具函数
- 保持文档与代码实际能力严格一致

---

## 8. 文档同步更新对照表

| 变更类别 | 必须同步更新的规范文件 |
|----------|------------------------|
| API 接口字段与事件 | `specs/api-conventions.md` 及相关文档 |
| 架构分层与目录组织 | `specs/architecture.md` |
| 检索算法、解析器与能力范围 | `specs/rag-and-retrieval.md`、`specs/product-scope.md` |
| 安全机制与鉴权控制 | `specs/security.md` |
| 工程规范与协作流程 | `specs/coding-conventions.md`、`specs/git-and-ai-hygiene.md` |

## 9. 任务完成汇报规范模板

任务执行完毕后，统一采用以下结构汇总汇报：

```text
## 变更内容
- ...

## 修改路径
- path/to/file1
- path/to/file2

## 未修改与边界范围说明
- ...

## 验证情况
- 执行命令：...
- 执行结果：...

## 文档同步
- [ ] 无需修改规范
- [ ] 已同步更新：specs/xxx.md

## 风险与后续注意事项
- ...
```

## 10. 合并前快速自检清单

**变更范围**
- [ ] 变更仅限于经批准的目标文件
- [ ] 未包含无关的代码重构

**版本控制**
- [ ] 未使用高危 Git 操作
- [ ] 未执行全局盲目暂存 (`git add .`)
- [ ] Diff 中无敏感密钥或临时生成物
- [ ] 提交信息符合 Conventional Commits 格式

**工程质量**
- [ ] 约定的自动化测试执行通过且输出真实
- [ ] 异常处理链路与租户作用域保持完整
- [ ] 规范文档与代码能力保持一致

---

## 11. 核心工程交付准则

AI 辅助开发的核心原则在于工程交付质量：确保变更范围精确、提交具备原子性、测试具备可复现性且技术文档保持诚实。
